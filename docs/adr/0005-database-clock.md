# ADR-0005. «Текущее время» во всех проверках берётся из часов PostgreSQL

- **Дата:** 2026-11-15
- **Статус:** Принято

## Контекст и ограничения

- Почти все правила брони сравнивают что-то с текущим моментом: запрос только до начала интервала (E8), результат
  проверки только строго до дедлайна (E10), отмена строго раньше начала (E12, E21), отметка в `[start, end)`
  (E17, E18, E22), таймеры дедлайна и окончания (S6), срок ключа повтора 24 часа (ADR-0003).
- Время проверяется на момент сохранения перехода, а не на момент поступления запроса (требования, «Участники
  и правила»). Граница секундная: запрос в 09:59:59 и сохранение в 10:00 дают разный результат (E21, E22).
- Сервис может работать в двух экземплярах (E27). Часы экземпляров расходятся на секунды, особенно в контейнерах
  на ноутбуках разработчиков. Если каждый экземпляр сверяет время по своим часам, граница «строго раньше начала»
  у них разная: один сохранит отмену, другой в ту же секунду откажет.
- Переходы уже выполняются условным `UPDATE` в PostgreSQL (ADR-0002), так что условие по времени удобно
  проверять в том же запросе.

## Решение

- Все сравнения с текущим временем выполняются в SQL через `clock_timestamp()` сервера БД. Часы экземпляра
  приложения (`DateTime.UtcNow`) в бизнес-правилах не используются.
- Переходы: условие по времени — часть условного обновления, например
  `UPDATE bookings SET status = 'cancelled' … WHERE id = :id AND status = 'confirmed' AND clock_timestamp() < start`.
- Синхронные проверки тоже по часам БД. Проверка `interval_started` в `POST /api/bookings` выполняется в той же
  транзакции, что и вставка Job: `INSERT … SELECT … WHERE :start > clock_timestamp()`. Если строка не вставилась,
  сервис отвечает `400 interval_started`. Так экземпляр с отстающими часами не примет запрос с уже наступившим
  `start`, который сразу ушёл бы в `timed_out`.
- `clock_timestamp()`, а не `now()`: `now()` в PostgreSQL — момент начала транзакции. Если транзакция ждала
  блокировку ресурса, `now()` окажется раньше фактического сохранения, и отмена, сохранённая в 10:00, пройдёт как
  сделанная в 09:59:59 (нарушение E21).
- Поля `createdAt` и `updatedAt` в ответах API заполняются тем же `clock_timestamp()`.
- Для тестов время подменяется SQL-функцией `app_now()`: в рабочей сборке она возвращает `clock_timestamp()`,
  в тестах — значение из настройки сессии `app.fake_now`. Все запросы вызывают `app_now()`, а не
  `clock_timestamp()` напрямую; в других ADR и в контракте для наглядности написано `clock_timestamp()`.

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---|---|
| Часы экземпляра (`DateTime.UtcNow`) и синхронизация по NTP | NTP уменьшает расхождение, но не убирает его: в `docker compose` на ноутбуке часы контейнера никто не настраивает. Граница всё равно разная у разных экземпляров, а E21 и E22 проверяют именно секундную границу |
| `now()` / `transaction_timestamp()` вместо `clock_timestamp()` | Время фиксируется в начале транзакции. Под блокировкой ресурса транзакция может ждать секунды, и проверка «строго раньше начала» выполнится по устаревшему времени |
| Абстракция `IClock` в приложении, время передаётся в SQL параметром | Легко тестировать, но параметр — это снова часы экземпляра: расхождение между экземплярами остаётся, а между вычислением времени и сохранением проходит ожидание блокировки |
| Сначала читать `SELECT clock_timestamp()`, потом сравнивать в C# | Два шага вместо одного: между чтением времени и `UPDATE` проходит время, и граница снова размыта |

## Цена решения

- Часть бизнес-правил по времени живёт в SQL, а не в доменном коде C#. Их нельзя проверить модульным тестом без
  базы — нужны интеграционные тесты с PostgreSQL (Testcontainers) и функция `app_now()` для подмены времени.
- Каждый разработчик должен помнить: никаких `DateTime.UtcNow` в правилах. Проверяем на ревью и правилом анализатора
  (запрет `DateTime.UtcNow` и `DateTime.Now` в проекте домена).
- Корректность зависит от часов одного сервера БД. Если они уйдут, ошибутся все экземпляры одинаково — граница
  останется единой, но сдвинутой. На сервере БД нужен NTP.

## Условия пересмотра

- Появятся реплики PostgreSQL для чтения или вторая база: тогда «часы БД» перестают быть одними, и нужен другой
  единый источник времени.
- Интеграционные тесты со временем станут слишком медленными или нестабильными для CI.
- Правила по времени понадобятся вне базы, например в отдельном сервисе или LLM-слое во втором семестре.
