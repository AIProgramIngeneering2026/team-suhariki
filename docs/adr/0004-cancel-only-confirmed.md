# ADR-0004. Отменить можно только подтверждённую бронь; запрос в проверке не отменяется

- **Дата:** 2026-11-15
- **Статус:** Принято

## Контекст и ограничения

- Пока Job в состоянии `requested`, его обрабатывает Dispatcher (ADR-0001). Карта К6: клиент передумал, пока задание
  выполняется.
- Бронь `requested` не занимает ресурс и не входит в лимит. Её проверка обычно занимает секунды, а если не успела —
  Job переходит в `timed_out` к началу интервала.
- Проверка не делает внешних действий: правила только читают данные, письмо ставится в очередь вместе с итоговым
  переходом. Прерывать «уже сделанную часть работы» не нужно — её нет.
- В требованиях S3 и E15 отмена разрешена только из «Подтверждена».

## Решение

`POST /api/bookings/{id}/cancel` разрешён только для `confirmed` до начала интервала. Для `requested` сервис отвечает
`409 invalid_state` с `details.currentStatus = requested`, состояние не меняется. Клиент дожидается итога проверки
и отменяет подтверждённую бронь; при подтверждении он получит письмо, при отмене — ещё одно.

Отдельного перехода `requested → cancelled` в диаграмме состояний нет ([job-states.md](../job-states.md)).

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---|---|
| Разрешить `requested → cancelled` | Добавляет гонку с Dispatcher: отмена и подтверждение должны стать взаимоисключающими, нужна ещё одна пара условных обновлений и тестов. Выигрыш — несколько секунд ожидания |
| Отмена `requested` как «пометка», которую Dispatcher учитывает перед подтверждением | Появляется скрытое промежуточное состояние «отменяется», которого нет в API и требованиях |
| Удаление Job (`DELETE /api/bookings/{id}`) | Пропадает история броней в «Моих бронях» (S5) и причина завершения |

## Цена решения

- Пользователь, передумавший сразу после отправки, ждёт итога проверки и делает второе действие; если бронь
  подтвердилась, придут два письма — о подтверждении и об отмене.
- Если проверка затянется из-за сбоя БД, пользователь не сможет снять запрос. Его закроет таймер к началу интервала,
  ресурс и лимит запрос при этом не занимает.

## Условия пересмотра

- Медиана времени проверки по метрикам больше 30 секунд или пользователи жалуются, что не могут снять запрос.
- Появится ручное согласование брони ответственным: тогда `requested` может длиться часами, и отмена запроса
  становится необходимой.
